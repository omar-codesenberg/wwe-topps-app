## 1. Sandbox setup walkthrough

This walkthrough takes you from a clean machine to a working sandbox checkout end-to-end. Allow ~45 minutes for the PayPal-side steps (account verification can stall on email confirmation). The PayPal Micropayments approval (step 9) is the only multi-day gate, and only blocks the LIVE rollout — sandbox development continues unblocked.

1. **Sign up at developer.paypal.com.** Use a personal Google or email account; this is the developer login, not the merchant of record.

2. **Create a sandbox Business account.** PayPal Dashboard → Testing Tools → Sandbox Accounts → Create Account → "Business". The sandbox auto-creates a paired Personal (buyer) account you can use to fund test purchases. Note both account emails.

3. **Create a REST app in the dashboard.** PayPal Dashboard → Apps & Credentials → Sandbox tab → Create App. Link the app to the sandbox Business account from step 2. After creation, copy the `Client ID` and `Secret` (revealed once — re-generate from the same screen if lost).

4. **Set Firebase secrets** for the sandbox Firebase project (per `[C4]` / `[S7]` env-prefixed naming):

   ```bash
   firebase use <sandbox-project-id>
   firebase functions:secrets:set PAYPAL_CLIENT_ID_SANDBOX
   firebase functions:secrets:set PAYPAL_CLIENT_SECRET_SANDBOX
   ```

   Each command prompts for the value and stores it in Cloud Secret Manager. Do not paste secrets into command history.

5. **Deploy functions once to obtain the webhook URL.** The webhook URL is generated by Firebase on first deploy — you cannot register a PayPal webhook before this step.

   ```bash
   firebase deploy --only functions:paypalWebhook
   ```

   Note the deployed URL from the CLI output. It will look like:
   `https://us-central1-<project>.cloudfunctions.net/paypalWebhook`

6. **Register the webhook in the PayPal dashboard.** PayPal Dashboard → Apps & Credentials → click your sandbox app → Webhooks → Add Webhook. Paste the URL from step 5. Subscribe to:

   - `PAYMENT.CAPTURE.COMPLETED` — finalizes purchases
   - `PAYMENT.CAPTURE.DENIED` — releases locked slots and surfaces failure
   - `PAYMENT.CAPTURE.REFUNDED` — closes the loop on auto-refunds (`[C7]`)
   - `PAYMENT.CAPTURE.PENDING` — log-only (per `[C10]`); used to detect eCheck holds and other pending instruments

7. **Capture the webhook ID and store as a secret.** The webhook ID appears in the dashboard immediately after registration. It is required to verify signatures via `/v1/notifications/verify-webhook-signature` (per `[C8]`).

   ```bash
   firebase functions:secrets:set PAYPAL_WEBHOOK_ID_SANDBOX
   ```

8. **Set `PAYPAL_ENV=sandbox`.** Per `[S7]`, validation in `functions/src/paypal/config.ts` is strict — module load throws if the variable is unset, or not exactly `"sandbox"` or `"live"` (case-sensitive).

   For Firebase Functions v2 (this project), the legacy `firebase functions:config:set paypal.env=sandbox` is **deprecated** (`[C16]`). Use a parameterized secret instead so the value is also access-controlled by Cloud Secret Manager:

   ```bash
   firebase functions:secrets:set PAYPAL_ENV   # value: sandbox
   ```

   Alternatively, for transient overrides during local testing only, you can use `--set-env-vars` on the deploy command. Pick one approach per project and stick with it; mixing the two routes leads to "why did my sandbox just hit live?" outages. **Recommended:** treat `PAYPAL_ENV` as a secret and set it identically to the credential bundle.

9. **Apply for PayPal Micropayments pricing on the LIVE account.** Go to your live PayPal Business account → Account Settings → Pricing → Micropayments. Approval typically takes 1–2 weeks and requires verifying your business / banking. **This step does NOT block sandbox development** — start it now and continue building.

After step 9 you can proceed with development against sandbox indefinitely. When the live account is approved AND code is ready, run the [going-live checklist](#5-going-live-checklist).

## 2. `priceCents` migration step (S1)

Before the first PayPal-aware deploy, all monetary fields in Firestore must be migrated from `price` (whole-dollar `number`) to `priceCents` (integer cents). Float64 storage is banned per `[S1]` because round-tripping `10.10` → `10.1` would break the strict-equality amount check at capture time (`[C2]`).

The migration is implemented in `scripts/migratePriceToPriceCents.ts`. It is idempotent — running it twice is safe; the second run finds nothing to do.

The script touches:

- `events/{eventId}/slots/{slotId}` — adds `priceCents = Math.round(price * 100)`, leaves `price` in place for backward read-compat (a follow-up purge happens after PayPal launch).
- `purchases/{captureId}` — same treatment for any historical receipts.

### Run the migration

Use a service account with Firestore write access. The script supports a dry-run mode that prints every change it would make without committing.

```bash
# Dry-run (safe; reports what would change, no writes)
GOOGLE_APPLICATION_CREDENTIALS=/path/to/key.json \
  npx ts-node scripts/migratePriceToPriceCents.ts

# Commit (applies writes)
GOOGLE_APPLICATION_CREDENTIALS=/path/to/key.json \
  npx ts-node scripts/migratePriceToPriceCents.ts --commit
```

### Verification after commit

Spot-check a handful of slot docs in the Firebase console — confirm `priceCents` is an integer matching `Math.round(price * 100)`. Do this before deploying the new functions; otherwise `createPayPalOrder` will throw on missing `priceCents` for any slot that didn't migrate.

## 3. App Check Debug Token registration (C14)

Per `[C14]`, App Check is enforced in **both** sandbox and live Firebase projects from day 1. This ensures the enforcement plumbing is exercised continuously in sandbox; production never discovers a misconfiguration for the first time under real money.

Dev devices (Expo Go on a phone, the iOS simulator, the web emulator, and CI runners) do not have valid attestation providers. They authenticate via App Check **Debug Tokens** registered in the Firebase Console.

### Onboarding a new developer / device

For each developer (or each device that needs to talk to a Firebase project), do the following:

1. Open the Firebase Console for the relevant project → App Check → Apps.
2. Click "Manage debug tokens" on the app entry that matches the platform (iOS, Android, Web).
3. Click "Add debug token". Generate a UUID locally (`uuidgen` on macOS) and paste it. Give it a descriptive name like `alice-iphone-15-dev` so future revocation is easy.
4. The developer pastes the token into their environment using the surface-appropriate mechanism:

   - **Expo Go (iOS / Android):** runtime env via the app config:
     ```
     EXPO_PUBLIC_FIREBASE_APPCHECK_DEBUG_TOKEN=<token>
     ```
     Add to a local `.env` file (gitignored) and restart `expo start`.

   - **Web emulator / browser:** in browser devtools console:
     ```js
     localStorage.setItem('FIREBASE_APPCHECK_DEBUG_TOKEN', '<token>');
     ```
     Reload the page.

   - **CI (GitHub Actions):** add a repository secret named `FIREBASE_APPCHECK_DEBUG_TOKEN` and reference it in workflow env. CI tests against the sandbox project only.

### Revocation

If a developer leaves or a device is lost, revoke the token immediately from the same Firebase Console screen. Tokens are independent — revoking one does not affect others.

**Live project hygiene:** dev debug tokens MUST NOT be carried into the live project. The live App Check config relies exclusively on real attestation providers (Play Integrity, App Attest, reCAPTCHA Enterprise). See [going-live checklist step 6](#5-going-live-checklist).

## 4. Local testing recipe

The PayPal sandbox webhook needs to reach a public URL. For local development the typical loop is: Firebase emulator + ngrok tunnel + sandbox webhook URL pointed at ngrok.

You'll need three terminals.

```bash
# Terminal 1: Firebase emulator (functions + Firestore)
firebase emulators:start --only functions,firestore
```

The emulator runs functions on port 5001 by default. The Firestore emulator runs on 8080.

```bash
# Terminal 2: ngrok tunnel pointing at the emulator
ngrok http 5001
```

Copy the `https://<random>.ngrok.io` URL ngrok prints. Construct the full webhook URL using your project ID and region:

```
https://<ngrok-id>.ngrok.io/<project-id>/us-central1/paypalWebhook
```

For example: `https://abc123.ngrok.io/breakbox-wwe/us-central1/paypalWebhook`.

```bash
# Terminal 3: anything else (logs, mobile dev server, etc.)
```

Then in the PayPal Dashboard → Apps & Credentials → your sandbox app → Webhooks, **temporarily** update the webhook URL to the ngrok URL. Remember to revert after local testing — otherwise webhook deliveries to the deployed sandbox stop.

### Local testing tips

- The ngrok URL changes every restart unless you have a paid ngrok plan. Re-update the PayPal webhook each time.
- Webhook signatures are still verified locally — the `PAYPAL_WEBHOOK_ID_SANDBOX` value must match the registered webhook (which it will, since you're using the same one).
- App Check enforcement is tunable in the emulator. If a debug token isn't getting through, set the `FIREBASE_APP_CHECK_DEBUG_TOKEN` env on the functions emulator process.

### Reading PayPal error codes in logs

PayPal returns two layers of error code on a failed call:

- **Top-level `name`** (broad HTTP category — e.g. `UNPROCESSABLE_ENTITY`, `AUTHENTICATION_FAILURE`, `INVALID_REQUEST`). Logged as `error.paypalCode`.
- **`details[0].issue`** (specific application code — e.g. `INSTRUMENT_DECLINED`, `PAYER_ACCOUNT_RESTRICTED`, `TRANSACTION_REFUSED`, `CARD_EXPIRED`). Logged as `error.issue`.

For triage, **`error.issue` is the field you want.** `paypalCode` is too coarse — virtually every Orders v2 capture failure surfaces the same `UNPROCESSABLE_ENTITY` at the top level.

```bash
# Cloud Logging filter — find every INSTRUMENT_DECLINED across the project
resource.type="cloud_function"
jsonPayload.error.issue="INSTRUMENT_DECLINED"
```

If `issue` is absent from a log entry, PayPal didn't supply a `details` array on that error (rare on Orders v2; common on auth errors). Fall back to `paypalCode` + `message` for those.

### Negative testing — forcing capture failures (sandbox only)

Two ways to validate that the app correctly refuses to finalize a purchase when PayPal declines the capture (low balance, restricted account, generic decline). Both should produce the same client-visible outcome: capture returns an error, the slot is not finalized, no `purchases/{captureId}` doc is written, and the slot lock releases on the next sweep.

**Option A — edit a sandbox buyer's funding (manual / exploratory):**

1. PayPal Dashboard → Apps & Credentials → Sandbox tab → Accounts → click your **Personal (Buyer)** account → `⋯` → **View/Edit Account**.
2. On the **Funding** tab, set the PayPal balance below the order amount (e.g. `$1.00 CAD` for a `$25` slot).
3. **Critical:** delete linked cards and zero out linked bank balances on the same screen. PayPal checkout will silently fall back to any working funding source — if you only lower the balance, the capture still succeeds.
4. Run the mobile flow against this buyer; PayPal's approval screen should block completion.

This is fine for one-off exploratory runs but is fiddly to set up and easy to misconfigure (a forgotten linked card masks the decline as a success).

**Option B (recommended) — deterministic mock responses via `PAYPAL_SANDBOX_MOCK_APPLICATION_CODE`:**

The capture path in [`functions/src/paypal/captureOrder.ts`](../functions/src/paypal/captureOrder.ts) reads `process.env.PAYPAL_SANDBOX_MOCK_APPLICATION_CODE` and, when set in a sandbox deploy, forwards it as PayPal's `PayPal-Mock-Response` header on the `/v2/checkout/orders/{id}/capture` call. PayPal's sandbox then returns a simulated `422 UNPROCESSABLE_ENTITY` with that application code, regardless of the buyer's actual funding. The flag is hard-gated on `PAYPAL_ENV === 'sandbox'` in code, so it is inert on live even if leaked into the wrong env file — but treat it as sandbox-only anyway and never set it on a prod project.

Useful codes (from PayPal's Orders v2 docs):

| Code | Simulates |
|---|---|
| `INSTRUMENT_DECLINED` | Low PayPal balance / card decline — buyer has no working funding source |
| `PAYER_ACCOUNT_RESTRICTED` | Buyer's PayPal account is restricted (holds, compliance) |
| `PAYEE_ACCOUNT_RESTRICTED` | Merchant account restricted (useful for going-live readiness checks) |
| `TRANSACTION_REFUSED` | Generic refusal — covers the broadest decline surface |
| `INTERNAL_SERVER_ERROR` | PayPal 5xx — exercises our `SanitizedError` 500-path |

**Run it against the emulator:**

```bash
# Functions emulator with the mock code injected
PAYPAL_SANDBOX_MOCK_APPLICATION_CODE=INSTRUMENT_DECLINED \
  firebase emulators:start --only functions,firestore
```

**Run it against a deployed sandbox** (do NOT do this against a prod project):

```bash
firebase use <sandbox-project-id>
firebase deploy --only functions:capturePayPalOrder \
  --set-env-vars PAYPAL_SANDBOX_MOCK_APPLICATION_CODE=INSTRUMENT_DECLINED
# When done, redeploy without the flag to revert:
firebase deploy --only functions:capturePayPalOrder
```

**Verification checklist for either option:**

- [ ] Cloud Logging shows `paypal_request_error` from `client.ts` with the expected `paypalCode` (e.g. `INSTRUMENT_DECLINED`).
- [ ] Cloud Logging shows `paypal_capture_failed` from `captureOrder.ts` immediately after.
- [ ] No `purchases/{captureId}` doc is written.
- [ ] The `paypalOrders/{orderId}` doc remains in its pre-capture status (not flipped to `captured`).
- [ ] The slot does NOT flip to `sold`; `releaseExpiredLocks` clears the lock on the next sweep (or the user can retry).
- [ ] Mobile client surfaces a "payment declined" error to the user.
- [ ] No refund is issued — there was no successful capture to refund.

## 5. Going-live checklist

Run these steps **in order**. Each step is a deploy gate — do not proceed until the previous step's verification passes. The numbered alerts in step 7 are the live-deploy gates from `[C12]`, `[C22]`, and `[S9]`.

1. **PayPal Micropayments approved on the live account.** Confirm by signing into PayPal Business → Account Settings → Pricing. Fee structure should show `5.0% + $0.05` for transactions ≤ $10 CAD.

2. **Create live REST app + live webhook subscription.** PayPal Dashboard → Apps & Credentials → **Live** tab (not Sandbox) → Create App. Link to the production PayPal Business account. Subscribe the webhook to the same four event types as sandbox (`PAYMENT.CAPTURE.COMPLETED`, `DENIED`, `REFUNDED`, `PENDING`).

3. **Create the production Firebase project** (or use an existing one):

   ```bash
   firebase projects:create wwe-breakbox-prod
   ```

   Skip if already created.

4. **Add the prod alias** so deploys are explicit:

   ```bash
   firebase use --add prod   # select wwe-breakbox-prod when prompted
   ```

   Verify with `firebase projects:list` and `firebase use`.

5. **CRITICAL — set ONLY `_LIVE` secrets on the prod project (per `[S7]`).** The production project must NEVER hold `_SANDBOX` secrets, and vice versa. C4's earlier "single project can hold both" allowance is retracted.

   ```bash
   firebase use prod
   firebase functions:secrets:set PAYPAL_CLIENT_ID_LIVE
   firebase functions:secrets:set PAYPAL_CLIENT_SECRET_LIVE
   firebase functions:secrets:set PAYPAL_WEBHOOK_ID_LIVE
   firebase functions:secrets:set PAYPAL_ENV   # value: live
   ```

   **Verification (must pass):**

   ```bash
   firebase functions:secrets:access PAYPAL_CLIENT_ID_SANDBOX --project prod
   ```

   Expected output: an error like `Secret PAYPAL_CLIENT_ID_SANDBOX not found`. **If this command returns a value, you have a `[S7]` violation — investigate immediately and destroy the sandbox secret on the prod project before proceeding.**

   Also confirm `firebase functions:secrets:access PAYPAL_ENV --project prod` returns exactly `live`.

6. **App Check is already enforced (per `[C14]`)** — no flip needed at cutover. Confirm the production attestation providers are configured:

   - iOS: App Attest provider registered in Firebase Console → App Check.
   - Android: Play Integrity provider registered.
   - Web: reCAPTCHA Enterprise site key configured.

   **Dev debug tokens MUST NOT exist in the prod project.** Audit Firebase Console → App Check → Apps → "Manage debug tokens" on each prod app — the list should be empty.

7. **Apply Terraform alert policies BEFORE first live transaction (`[S12]`).** Alert policies are committed to the repo at `infra/terraform/paypal-alerts.tf` (owned by team T1). Apply them against the production project:

   ```bash
   cd infra/terraform
   terraform plan -var-file=prod.tfvars
   terraform apply -var-file=prod.tfvars
   ```

   Required alerts (these are the live-deploy gates):

   | Tag | Condition | Window |
   |---|---|---|
   | `[C12]` | `pendingRefunds.status === 'alert_required'` count > 0 | 1 min |
   | `[C22]` | `systemState/refundQueueHalted` doc exists | (existence check) |
   | `[S9]` | `paypal_amount_mismatch` log-event count > 0 | 5 min |
   | `[S3]` | `paypal_webhook_verifier_failure_response_count` > 0 | 5 min |
   | `[S3]` | `paypal_webhook_verifier_call_error_rate` > 1% | 5 min |
   | `[S19]` | `paypal_order_creation_rate` threshold breach (calibrate post-launch) | 1 min |

   **Test EACH alert end-to-end:** trigger the condition (e.g. write a fake `pendingRefunds` doc with `status: 'alert_required'` then delete it), confirm the alert fires and the page lands. Do not skip — alerts that have never fired have never been validated.

8. **Deploy functions and rules:**

   ```bash
   firebase deploy --only functions,firestore:rules --project prod
   ```

9. **Smoke test with a real card and a real $1 slot.** Create a $1 test slot via admin, run the full mobile flow end-to-end with a personal credit card. Verify:

   - Funds settle to the live PayPal Business account (visible in PayPal dashboard → Activity).
   - `purchases/{captureId}` doc exists in Firestore with `userId`, `eventId`, `slotId`, `priceCents = 100`, `status = 'completed'`.
   - The slot flips to `sold` with `transactionId === captureId`.
   - Cloud Logging shows the `correlationId` (`[S16]`) tying the order → capture → finalize sequence together.

   Then immediately refund yourself via the admin tools to confirm the refund path works on live.

10. **Update the mobile app to point at the production project.** This is env-driven via `app.config.js` reading `EXPO_PUBLIC_FIREBASE_PROJECT_ID` (and friends). Build a release candidate against prod config.

11. **Migrate `wwebreakbox://` to Universal Links / App Links per `[C13]`** BEFORE App Store submission. The custom-scheme deep link is acceptable for sandbox but allows other apps to register the same scheme and intercept the PayPal return. Universal Links / App Links bind to your verified domain and cannot be hijacked.

12. **Submit to App Store / Play Store / deploy web with prod config.** Be aware the App Store review can take 1–7 days; plan launch comms accordingly.

13. **Remove the legacy `purchaseSlot` callable export.** After verifying no client code references it (`grep -r purchaseSlot src/ admin-web/`), delete `functions/src/purchaseSlot.ts` and remove its export from `functions/src/index.ts`. This eliminates the bypass-PayPal code path entirely. Deploy and verify no client errors.

## 6. Secrets rotation cadence (S15)

Per `[S15]`, the env-prefixed secret bundles support rolling rotation: write a new version, redeploy to pick it up, then retire the old version. No flag-day downtime.

| Secret | Cadence | Procedure |
|---|---|---|
| `PAYPAL_CLIENT_SECRET_*` | Every 90 days | See "Client secret rotation" below |
| `PAYPAL_WEBHOOK_ID_*` | On incident only | Webhook subscription must be recreated in PayPal dashboard first; then `firebase functions:secrets:set PAYPAL_WEBHOOK_ID_<ENV>` and redeploy |
| `PAYPAL_CLIENT_ID_*` | Same as secret (rotate together) | The client ID and client secret are issued as a pair; rotate them as a pair |

### Client secret rotation procedure

1. **Generate a new secret in the PayPal dashboard.** Apps & Credentials → your app → Add Secret. PayPal allows two active secrets per app, which is what makes zero-downtime rotation possible.

2. **Write the new secret as a new Cloud Secret Manager version:**

   ```bash
   firebase functions:secrets:set PAYPAL_CLIENT_SECRET_<ENV>   # paste new value
   ```

3. **Redeploy functions to pick up the new version:**

   ```bash
   firebase deploy --only functions
   ```

4. **Verify the new credential is in use** by checking a recent log entry from `functions/src/paypal/client.ts` — the OAuth token call should succeed with the new credential ID. If you have a structured log emitting the resolved client ID prefix, confirm it matches the new value.

5. **Retire the old secret version** from Cloud Secret Manager (so an attacker with the old value cannot replay):

   ```bash
   firebase functions:secrets:destroy PAYPAL_CLIENT_SECRET_<ENV>:<old-version>
   ```

6. **Revoke the old secret in the PayPal dashboard.** Apps & Credentials → your app → click the old secret entry → Revoke.

Set a 90-day calendar reminder for the next rotation. Track rotations in your team's secrets-rotation log so on-call can verify the last rotation date during incidents.

## 7. Refund queue circuit-breaker recovery (C22)

Per `[C22]`, the refund retry scheduler (in `functions/src/paypal/pendingRefundsRetry.ts`) implements a global circuit breaker. If three or more refunds fail in a 1-hour rolling window with the same permanent error code (e.g. `INSUFFICIENT_FUNDS`), the scheduler writes `systemState/refundQueueHalted` and pages on-call. While that doc exists, the scheduler skips its run — the queue does NOT drain, and no further refund attempts are made.

This is intentional. A merchant-side problem (zero balance, account hold) will cause every refund to fail; without the breaker the queue would burn PayPal API quota and potentially trip PayPal's fraud detection.

### Recovery steps

1. **Page received.** Investigate WHY refunds are failing with permanent codes. Check Cloud Logging filtered to `pendingRefunds` writes; look at the `errorCode` and `errorMessage` fields.

2. **Identify the root cause.** Common causes:

   - **Merchant balance insufficient.** PayPal Business account does not have enough funds to issue refunds. Add funds via the PayPal dashboard (transfer from linked bank, or wait for in-flight settlements).
   - **Account hold.** PayPal compliance has placed a hold on the account (review request, identity reverification, suspicious activity). Resolve via PayPal support — there is no API workaround.
   - **PayPal fraud system flagged the refund pattern.** Unusual refund volume can trigger automated detection. Contact your PayPal account manager.
   - **Permanent decline on a specific instrument** (`INSTRUMENT_DECLINED`, `REFUND_NOT_ALLOWED`). The buyer's card was closed; PayPal cannot issue a refund to it. Manual reconciliation required (see step 5 below).

3. **Once the underlying issue is resolved,** clear the halt flag:

   ```bash
   gcloud firestore documents delete systemState/refundQueueHalted --project=<project>
   ```

   (Or delete via the Firebase Console UI.)

4. **Wait for the next scheduled run** (every 15 min). Confirm the queue drains by checking the count of `pendingRefunds` docs with `status === 'failed_will_retry'` in Cloud Monitoring — it should trend downward. New successful refunds flip docs to `status === 'completed'`.

5. **Manual reconciliation for permanent failures.** Refunds with `status === 'alert_required'` (per `[C22]`'s permanent-error classification) cannot be auto-retried. For each:
   - Open `pendingRefunds/{captureId}` in Firestore; note the `errorCode` and `userId`.
   - Contact the user via support channel; offer manual refund (PayPal dashboard → Activity → find capture → Refund) or alternative resolution (store credit, replacement slot).
   - Once resolved, manually flip the doc to `status === 'manually_resolved'` with a `resolutionNote`.

### Critical: do NOT manually clear `pendingRefunds` docs

Deleting `pendingRefunds/{captureId}` removes the decision-lock (per `[S10]`) and breaks idempotency between the mobile and webhook refund paths. The retry function and scheduler handle the docs — leave them alone unless you are also flipping the corresponding `purchases/{captureId}` state.

## 8. Common errors and troubleshooting

Filter Cloud Logging by the structured event names in the left column to find occurrences. Every entry includes a `correlationId` (`[S16]`) that ties together every log entry from order creation through capture, webhook, finalize, and refund — paste a `correlationId` into a Cloud Logging filter to see the full timeline of one transaction.

| Error / log event | Likely cause | Fix |
|---|---|---|
| `paypal_amount_mismatch` (`[C2]` / `[S9]`) | Slot price changed mid-checkout, OR client sent a stale order from a forked flow, OR test malice. | An auto-refund is already issued via the `[C7]` idempotent path. Investigate via `correlationId`: check whether the user's `expectedAmount` matches the slot's current `priceCents` at the time of capture. If the slot was admin-edited mid-flow, that's the cause. |
| `paypal_custom_id_mismatch` (`[S5]`) | The `custom_id` returned by PayPal does not match the `paypalOrders/{orderId}` doc. Indicates either a cross-merchant misconfiguration (webhook bound to the wrong PayPal app) or a webhook handler bug. | Verify the webhook subscription in PayPal dashboard is bound to the correct app (sandbox vs live) and pointed at the correct Firebase project URL. If misconfigured, re-register and rotate `PAYPAL_WEBHOOK_ID_*`. |
| `paypal_webhook_verifier_call_error` rate spike (`[S3]`) | PayPal verifier endpoint outage OR our credentials revoked. | Check the [PayPal status page](https://www.paypal-status.com/). If it's green and our errors continue, our OAuth credential has likely been revoked (manual revocation in dashboard, or hit a rate-limit ban from `[S4]` regression). Rotate `PAYPAL_CLIENT_SECRET_<ENV>`. |
| `paypal_webhook_verifier_failure_response_count` > 0 (`[S3]`) | Verifier returned a definitive `FAILURE` — incoming webhook signature did not validate. | Either an attacker forged a webhook (block at infra), OR the `PAYPAL_WEBHOOK_ID_<ENV>` secret is mismatched with the registered webhook. Re-check the webhook ID in the PayPal dashboard against the secret value. |
| `RATE_LIMITED` from `createPayPalOrder` (`[C20]`) | Single user holding ≥ 5 active orders across all slots. | Likely abuse. Investigate the user via `correlationId` — pull their recent `paypalOrders` docs and check whether they're abandoning checkout flows (lock-exhaustion DoS pattern) or have a legitimate UX problem. |
| `ORDER_ALREADY_OPEN` from `createPayPalOrder` (`[S2]`) | User retried `createPayPalOrder` for the same (uid, slotId) within the lock window. | No action needed — this is the normal "resume, don't fork" path. The response includes the existing `{orderId, approveUrl}` and the UX surfaces the existing approve link. |
| `failed_will_retry` (multiple, transient) on `pendingRefunds` | PayPal API instability — 5xx, timeout, or transient rate-limit. | Wait 15 min; the scheduler retries. Watch for the `[C22]` circuit breaker — three permanent failures of the same code in 1h flips to `refundQueueHalted`. |
| `alert_required` (single, permanent) on `pendingRefunds` | PayPal returned a permanent failure code (e.g. `REFUND_NOT_ALLOWED`, `TRANSACTION_REFUSED`). | Check `pendingRefunds/{captureId}.errorCode`. The refund cannot proceed automatically — see [section 7, step 5](#7-refund-queue-circuit-breaker-recovery-c22) for manual reconciliation. |
| Slot stuck in `locked` state with no `paypalOrders` doc | User abandoned mid-checkout; lock is awaiting expiry. | No action — `releaseExpiredLocks` (`functions/src/releaseExpiredLocks.ts`) clears it. If urgent, manually clear via Firestore console (`lockedBy: null`, `lockedUntil: null`). |
| Mobile capture returned success but slot still shows available | Mobile call succeeded server-side but client never received the response (network blip). The webhook will finalize. | Wait up to 30 seconds for webhook delivery. Verify `purchases/{captureId}` exists. If the slot didn't flip, check `webhookEvents/{transmissionId}` for a record of the delivery. |

### Finding a transaction by user

```bash
gcloud firestore documents list purchases \
  --filter='fields.userId.stringValue=<uid>' --project=<project>
```

Or use the Firebase Console → Firestore → `purchases` → filter by `userId`.

## 9. Abuse-signal monitoring (S20)

For v1 this section is **observe only** — no automated gating. Add gating later when abuse actually surfaces. Premature gating creates more false-positive support load than it prevents fraud at small scale.

### Signals to dashboard

Set up Looker Studio or Cloud Logging dashboards to track:

- **Velocity of distinct accounts from a single IP.** Aggregate `createPayPalOrder` log entries by source IP (from request metadata). A single IP creating orders for ≥ 5 distinct `userId` values within 1 hour is a multi-account abuse signal.
- **Sub-1-hour-old account purchases.** Join `createPayPalOrder` events against the auth user's `creationTime`. A high ratio of purchases from accounts created < 1 hour ago suggests scripted account creation.
- **App Check failure rate.** A spike in App Check rejections suggests either an attacker bypassing the mobile app, OR a real attestation provider outage. Investigate.
- **Average orders-per-account-per-hour.** Establish a baseline post-launch. A user creating 10+ orders/hour (even legitimate ones) deserves a manual look.
- **Global per-minute order-creation rate** (`[S19]`). Already alerted via Terraform; also chart it over time to spot trends below the page threshold.

### Mitigations to add IF abuse surfaces

In rough order of escalation:

1. **CAPTCHA on checkout.** Add reCAPTCHA Enterprise (already integrated for App Check Web) as a second gate before `createPayPalOrder`.
2. **Account-age gating.** Reject `createPayPalOrder` if `auth.creationTime < 24 hours ago`. Affects new-user UX, so deploy with a feature-flagged rollout.
3. **Per-IP order rate cap.** Add an IP-keyed counter (Firestore or Cloud Memorystore) capped at N orders/min. Pairs poorly with shared IPs (corporate NAT, mobile carriers); use as a last resort.

Document any gating rule additions in a follow-up runbook section, including the trigger that made it necessary, so future on-call can understand the constraint.
